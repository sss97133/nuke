# Offline source disposition bridge

`source_disposition.py` consumes a frozen, permission-scoped Photos metadata snapshot and emits a deterministic accounting manifest. It does not read Photos, inspect image content, call a model, upload, file a vehicle or call Supabase. The `assets` array accepts `LibraryCandidateDiscovery.Asset` fields (`id`, `sourceVersion`, capture clock, nullable GPS and local labels), with optional `mediaKind: image|video|screenshot`. The native Library export currently supplies images only. A video count outside that selector must be declared, never silently counted as an enumerated image.

```sh
python3 scripts/photo-pipeline/source_disposition.py /private/input.json /private/output.json
python3 -m unittest discover -s scripts/photo-pipeline -p 'test_*disposition*.py'
```

The executable metadata connection is `native_disposition_adapter.py`: pass the existing `apps/nuke-capture-ios/scripts/discover-library-candidates/main.swift` JSON input and output, plus the source export's observed time, stable library namespace, actual permission scope and separately known video count. The replay producer emits `inputSha256` over its exact stdin bytes; the adapter checks that fingerprint before binding candidates. Old output without the fingerprint must be regenerated by the local deterministic selector, never stamped retrospectively. Changed source versions, target vehicle, seed IDs or discovery settings invalidate the binding. It binds every candidate to the current source version and writes the frozen bridge input and held manifest. It intentionally supplies no original-byte, existing-leaf, filing or privacy facts; the existing source and intake owners must populate those from real evidence. Example for a private sample:

```sh
python3 scripts/photo-pipeline/native_disposition_adapter.py \
  /private/native-input.json /private/native-output.json /private/held-manifest.json \
  --snapshot-id retained-sample-1 --observed-at 2026-11-15T12:00:00Z \
  --source-namespace owner-library-sample --access-scope sample \
  --videos-outside-selector 19 --input-output /private/frozen-input.json
```

The native export currently gives metadata for permission-visible **images only** and no source library namespace, original bytes, server leaf/currentness proof, privacy decision, or supported filing decision. The adapter requires the exporter/operator to supply the first two scope facts and leaves the rest held. It cannot establish complete library coverage or video disposition from the image-only native export.

Input shape:

```json
{
  "schemaVersion": 1,
  "intendedUse": "vehicle_gallery",
  "snapshot": {
    "snapshotId": "stable source-export identifier",
    "sourceNamespace": "stable owner-library or device namespace",
    "observedAt": "2026-11-15T00:00:00Z",
    "accessScope": "full",
    "declaredAssetCount": 1,
    "mediaCoverage": {"imagesEnumerated": true, "videosEnumerated": false, "knownVideosOutsideSelector": 0},
    "assets": [{"id": "PhotoKit localIdentifier", "sourceVersion": "modification-date hint", "mediaKind": "image", "captureAt": null, "latitude": null, "longitude": null}]
  },
  "candidates": [{"id": "PhotoKit localIdentifier", "sourceVersion": "modification-date hint", "reasons": ["near_anchor_time"]}],
  "sourceFacts": {},
  "priorSourceIds": [],
  "withdrawnSources": []
}
```

`expectedSnapshotSha256` can pin the exact frozen snapshot on replay. Duplicate IDs, count drift, unknown or stale-version candidate IDs, stale source facts and hash mismatch fail before output. JSON key and asset order do not affect hashes. Missing `priorSourceIds` are reported in `priorAbsenceUnknown`, not called withdrawn: a sample or limited permission view cannot prove removal. A withdrawn row requires an explicit `withdrawnSources` entry with `kind: photokit_removed_from_permission_scope`, matching `sourceNamespace`, and a nonempty `evidenceId` from the PhotoKit change or permission record.

An optional `sourceFacts[id]` must carry the current `sourceVersion`. `original` and `rendition` are separate `{sourceVersion, sha256, byteSize, mimeType}` facts about actual bytes, not preview guesses. `existingLeaf` is `{imageId, sourceNamespace, sourceId, sourceVersion, byteRole, sha256, visibility: current, isSuperseded: false, supersededBy: null, sourceBindingId}` and reconciles only when namespace, source ID/version, both currentness controls and the selected role's byte hash agree. A filename, clock, perceptual hash or similar looking copy never substitutes for this. A `supported_complete` filing additionally needs matching `sourceNamespace`, `sourceId`, `sourceVersion`, `imageId`, the manifest's `intendedUse`, and a `decisionId` plus `witnessId`; an unsupported raw status becomes disputed. `privacy: {status: clear, sourceVersion, intendedUse, decisionId}` is necessary for an admission proposal or completed filing. A personal or screenshot control requires a separate current `mediaPolicy` with the same scope and a `decisionId`; a reviewed screenshot can advance. `selectedForAdmission: true` is a separately supplied selection fact, not generated from a discovery candidate. An unassigned source proposal requires current original bytes, current privacy clear and explicit selection, and carries `vehicleId: null`. It is an inspection artifact for the existing identity-first writer, not an RPC payload; storage URL/path, owner and request context still belong to that existing intake owner. Partial/disputed filing, transformed-copy ambiguity and videos do not produce proposals.

The output has one row per current source plus explicitly evidenced withdrawn IDs, partitioned into `version_unverified` (a null PhotoKit modification hint), `original_unverified`, `source_unavailable` (only with explicit `originalStatus: unavailable`), `identity_ambiguous`, `partial`, `disputed`, `privacy_hold`, `candidate_unreviewed`, `unselected_source`, `ready_source_admission`, `admitted_unresolved`, `supported_complete`, `unsupported_video` or `withdrawn`. Each row names its next dependency. The manifest retains a digest of **all** supplied source facts and the privacy, media and filing decision IDs, so changing proof changes `manifestSha256` even when a disposition stays the same. `recordedFilingStatus` is an input assertion; `qualifiedCompleteFiling` is the strict source/leaf/privacy/use-scoped result. Candidate reasons remain retrieval evidence. A source may have multiple supported vehicle or depicted-subject relationships; this manifest never collapses those into a single inferred `vehicleId`. The output's `snapshotSha256` and `manifestSha256` make the frozen input and disposition replayable.

Retained metadata replay (private files in `~/nuke-logs/library-context-discovery-20261115/`) has 347 images on seven sampled dates, 141 discovery candidates, 19 videos known outside the image selector, and no original-byte, privacy or exact existing-leaf facts. The bridge correctly emits 347 `original_unverified`, 175 missing-GPS context reasons and **zero proposals**. This is not a full Photos inventory or a finding that all 347 originals are genuinely unavailable; the retained replay simply did not supply their original-byte evidence. Add current source facts only after inspecting actual originals and exact existing leaves.
