# Direct inputs behind canonical material checks

The builder needs to inspect a held quantity or specification and see the exact input that produced its verdict. Existing `harness_model_checks` retain a typed subject and rule version, while the whole evaluation retains the private input/code receipt. Add direct field edges to that existing check owner; do not create another evaluator, source claim, BOM or scheduler.

`harness_model_segment_check(text,jsonb)` is a canonical substep of `harness_model_compute`. It selects a closed set of projected-segment fields, fingerprints their presence and value, and evaluates the predicate using only those selected values. The five predicates are `segment_specification`, `wire_stock_key`, `material_source_status`, `new_wire_demand` and `planned_wire_amount`. Verdict semantics and material quantities are preserved. Unknown predicates return no instrumentation, rather than fabricated empty coverage.

`harness_model_check_inputs` has one row per check and declared direct field. Its composite check/evaluation FK and typed segment FK retain the exact result and physical-piece revision. Presence distinguishes an absent field from explicit JSON null. A statement trigger validates each inserted batch against captured segment projections and their canonical predicate results, expanding each evaluation only once. Existing append-only enforcement retains the derived history. Values remain in the input owner; the child stores a change fingerprint, not a second value.

The existing fold saves these children atomically with the checks, records expected per-check and evaluation counts, and publishes through the same cursor. The shared receipt refuses incomplete visible children, so all bounded manual consumers and the bulk diagnostic retain one completeness decision. Predicate/guard code enters the existing logic fingerprint. Source changes retain the existing source-trigger/worker path; no queue, pressure control, source write or forced fold is added.

`harness_model_check_context(vehicle,evaluation,check)` inspects one current check. It captures the current invoker-visible, allowlisted model, verifies the shared receipt and exact evaluation, and returns at most four direct field values after matching their presence/fingerprints. A closed subject summary supplies gauge, expected gauge/part and length context. It exposes no private input or logic receipt. Wrong, stale, withdrawn or incompletely visible evaluations return no check/value payload. Uninstrumented rules explicitly report `not_recorded`.

These are **direct predicate inputs in the evaluated segment projection**. Fields such as `specification_state` and `physical_progress` are themselves derived. Transitive base-field/source/witness lineage remains `not_assessed`, and no nearby observation is claimed as consumed evidence. This does not complete electrical sizing, engineering coverage, purchasing, measured cuts or the public builder handoff.

Contract: `supabase/sql/test_harness_check_field_bindings.sql`. It reuses existing source fixtures and preserves golden results across unknown/conflicting/physical-progress cases and 500 pieces; tests persisted FK/value admission, absence/null distinctions, public inspection/private receipt isolation, hidden-child completeness, append-only history, source changes and interpreter changes. The unchanged existing 500-piece source population is factored into one fixture helper for both the original evaluation contract and the new complete-producer assay. Runtime and deployed acceptance remain separate from these disposable tests.
