# Image keys build design, 2026-11-10: the two judgments

Two adversarial judges read `2026-11-10_image-keys-build-design.md` against the code. One judged by the owner's
rules and by truth, the other by whether it can be built and run. Each scored it 6 of 10. Only one of three
commissioned designs was delivered, so neither judgment is a comparison. Repo only; an audit output to verify.

## Judged by the owner's rules and by truth

The only design delivered. It is the owner's model in the right places: parts in subject_taxonomy, kinds of imperfection in condition_taxonomy (a real descriptor_id column on the log, shared with text claims), states as observation_properties rows, values and 'what each looks like' in one new column, questions built by one SQL function from registry rows, closed answers in the existing evidence_judgment_requests store, landing through ingest-observation with one witness row per photo, no claims table, the claim and its level of proof computed in a fold. It does not overwrite or delete testimony, bakes no categorical into schema, and its one new table is attached, described, owned and read. I opened the code behind its load-bearing claims and most are true (the code list that refuses a key before the registry is read, both judgment guards hard-wired to one kind, one witness per observation, the batch path closed to owner photos, no answerer in the repository, supersede needs a user session, the guardrail STOP). It loses four points because several of its own mechanisms do not work as written: the proposal path cannot approve its two new proposal types (quorum is 9999 for an unknown type); growing a value list withdraws every answered question of that property, so growth un-proves the data; a rolled-back answer counts again once the question is re-answered; the owner's-word level cites a mechanism that is not the one in the code and is enforceable only in the edge function; a change between two dated photo sets is written automatically as a work record with no proof threshold; an imperfection's identity is only part plus kind; the place is not written in real time by default and the proposal queue has no drain; questions exist only where an earlier free-text reader already spoke; and the owner sees nothing about his truck until the seventh pull request. Nothing was executed; all SQL is unrun.

### Claims in the design found false

- Section 6.4 and the consistency summary: 'Approval is the existing review insert. On approval the new apply branch inserts the subject_taxonomy or condition_taxonomy row.'
  In fact: False for the two new types as designed. fn_schema_proposal_required_approvals returns 9999 for any proposal type it does not list (supabase/sql/test_schema_proposal_add_source_contract.sql:131-147, frozen from production), so one review never approves add_subject or add_descriptor and the apply branch never runs. The design does not list that function among those it extends.
- Section 5.3: the owner's confirmation is a row with extraction_method 'owner_confirmed_v1' (the method agent-chat already writes) 'which gets the +0.30 at ingest-observation/index.ts:1165'.
  In fact: The +0.30 is given for structured_data.owner_confirmed === true (supabase/functions/ingest-observation/index.ts:1165); extraction_method plays no part. The cited pattern writes with the service key (supabase/functions/agent-chat/index.ts:428-441), which the design's own new rule would refuse.
- Section 8.6: 'With no frontend change, after the first landing' the owner sees the proof car in 'the field drill: get_field_provenance(vehicle, part_paint_stage) ... hook useFieldProvenance.ts:171'.
  In fact: The function would return the rows, but no page calls it for a part property. VehicleEvidenceView has five fixed fields (nuke_frontend/src/pages/vehicle-profile/VehicleEvidenceView.tsx:12-18, :32) and VehicleDossierPanel asks for engine and VIN fields (:586-588). Without a frontend change the only existing surface is the observation timeline.
- Sections 5.2, 6.3 and the risk table: a bad placement run is undone with reopen_evidence_judgment_answers and 'everything landed from it leaves the counts'.
  In fact: Only until the question is answered again. Reopen returns the same question id to pending (supabase/migrations/20261111210500_receipt_work_reconciliation.sql:703-712); once re-answered its status is 'answered' and the rows from the rolled-back answer, which carry that judgment id, pass the fold's test again.
- Section 5.2 and pull request 5: vehicle_part_claims and the measure are 'replayable by as-of date'.
  In fact: Overstated. The fold filters observations by ingested_at but reads each question's status as it is at call time, so a past as-of does not reproduce what the fold returned then once any question has been withdrawn, retired or reopened since.
- Section 13.3 decision 3 and the summary: part claims are readable by 'owner and service role only in this build'.
  In fact: Contradicted by the design's own section 8.5 (the fold is granted to authenticated with a public branch) and by the existing row policy, under which a condition row on a public vehicle is readable by others (supabase/migrations/20260928233000_observation_privacy_marking.sql:59-74). True only if the proof car is private, which has not been read.
- Summary and section 0: 'Count of new things: ... Four existing SQL functions and one edge function are extended.'
  In fact: Undercounted. To work as described it must also replace fn_schema_proposal_required_approvals and schema_proposal_evidence_check, and change the add_property branch to carry value_spec. That is at least six existing SQL functions, each needing an md5 guard against its live body.

## Judged by whether it can be built and run here

The only design that was delivered. Its skeleton is right and almost every load-bearing code claim checked out when I opened the file (writer code list at ingest-observation/index.ts:979-984, both judgment guards hard-wired at 20261111210500:408 and :623, one witness per observation at 20261002213353:45-71, batch path closed to owner photos at 20261004064216:94/127/133, no answerer in the repo, supersede needs auth.uid, Mac lane has claude -p and the service key). It follows the capability map's named owner (CAPABILITY_MAP.md:127), passes the new pull-request gate (I ran no-new-photo-reader's test on its script paths and table: clean), uses only sanctioned writers, keeps not-visible and cannot-tell out of testimony, and computes the claim as a fold instead of a claims table. It loses four points on what the brief asked me to prefer and on things that break: (1) its first pull request shows nothing on the first vehicle and replaces a live approval function; the first vehicle rows first land at pull request 7, after five migrations, a change to the sole writer and a new trigger on the largest testimony table; (2) its two new proposal types can never be approved, because the live quorum function returns 9999 for any unlisted type; (3) its placement answer holds one part and one state per sentence, and 11 of the first vehicle's 30 callouts hold two; (4) the part key is put in JSON without bringing that choice to the owner, against the theory card; (5) proposal evidence would copy phrases and ids from private photos into a table whose only definition in the checkout is readable by everyone; (6) a fold bug, an under-counted photo-call estimate, and an ordering hazard that could 503 every property-keyed intake.
