# The one map (plan and pre-mint memo, 2026-10-19)

**Status:** plan, approved by the owner 2026-10-19 (~18:00 UTC). Nothing below is built unless a step says so.

## Owner direction

"We shouldn't have multiple maps. We should have one map that is a tool to navigate any bit of map-oriented data."
"It needs to be really fast; it can't be glitchy. The ontology is confused; it must be deterministic." The model is the
iOS map (`apps/nuke-capture-ios/Sources/NukeCapture/MarketMapView.swift`, `CountyZIPDrill`): one surface where zoom
sets the level (state → county → ZIP → point), tap an area for its activity. Full redevelopment, web and iOS.

## What exists (read 2026-10-19)

| Surface | What it is | Problem |
|---|---|---|
| iOS `MarketMapView` / `CountyZIPDrill` | MapKit; zoom-driven scale; ZIP polygons fetched live per county from Census TIGERweb; counts folded on the phone by paging every `vehicle_location_observations` row of the counties in view; make + date filters; ZIP activity sheet (vehicles, listings, businesses, sellers, auction events) | slow and fragile by design: live third-party geometry, client-side counting |
| web `/atlas` `NukeMap` | deck.gl dots of location observations + org pins + timeline | drew nothing until #2209 (string coordinates); no area level |
| web `/map` | was `PublicMap` (organizations); since #2215 `CountyListingMap` (listings per county, Leaflet) | a third concept, not the iOS model |
| web `ChoroplethMap` county mode | Leaflet county shading of `vehicle_map_county_data` | its refresh job `refresh-geo-analysis` is inactive; vehicles × sold value only |
| `MarketGeographyMap`, `ImageLocationMap` | unused / per-vehicle photo widget | dead / separate |
| Market tab "maps" (web + iOS treemaps) | brand/family boxes | not geographic; out of scope |

## The ontology (step 1): one definition per layer

Every layer is defined once, in the database, by: entity counted, source table, inclusion rule, clock, geographic
precision, value basis. A count on the map always means exactly one of these.

| Layer | Entity (counted once) | Source and rule | Clock | Geography | Value |
|---|---|---|---|---|---|
| `listing` | vehicle | `vehicle_location_observations` `source_type='listing'` (all sources; `source_platform` is the source facet) | first listing observation in the window | the observation's keys | asking price (`vehicles.asking_price`) |
| `sale` | vehicle | `vehicle_events` with `sold_at` (`event_status` sold), placed by the vehicle's location observation for that listing (`source_url` / platform match), else its latest public location | `sold_at` | that observation's keys | sale price (`vehicle_sale_basis()`) |
| `vehicle` | vehicle | any public location observation | latest observation | latest observation's keys | none |
| `organization` | organization | `organizations` (public) with coordinates, plus `organization_locations` | current (no history) | its point | none |
| `photo` | image | `vehicle_images` approved, public vehicle, with GPS, **never shown as points**; aggregated to ZIP/county only | `taken_at` | point → ZIP/county | none |

Rules that make it deterministic:
- Public, undeleted vehicles only; the public test happens once, in the fold, never at page time.
- A vehicle counts once per layer per window, at the place of the observation the rule names.
- Every count carries its `as_of`; unknown clocks are excluded from date windows and counted separately.
- Asking prices, sale prices and bids are different measures and never summed together.

## Geography (step 2)

Place entity levels (extends C8, which declared `us_county_boundaries` at county grain "until a reader needs" more):
- **state**: `left(county_fips, 2)` with a name table (56 codes incl. territories).
- **county**: `us_county_boundaries` (exists, GIST indexed).
- **ZIP**: Census 2020 ZCTA polygons, simplified (cartographic boundary file), loaded into PostGIS as reference data
  with source + vintage columns; `vehicle_location_observations.zcta` keyed by trigger (postal code when it is a ZCTA,
  else point-in-ZCTA), like the county key (#2213).
- Open: size budget for ZCTA geometry on the production database (measure before loading; simplify to fit).

## Facts (step 3): precomputed, never counted live

`map_facts`: grain (level, area_key, layer, source_platform, day) → entities, priced, value_sum, as_of. Written by one
fold per layer, incrementally (recent days every 10 min; full rebuild nightly). Reason: a live count must join each
located vehicle to `vehicles` for the public test; on 2026-10-19 a 3-day listing window took 5.2 s (2,092 lookups,
1,411 pages from disk). `vehicle_map_county_listings` (#2215) becomes the `listing` fold's first version.

## Serving (step 4)

- **Boundaries**: static vector tiles (state/county/ZIP) built once into storage, CDN-cached, shared by web and iOS.
  No live TIGERweb calls. Tooling: a Node pipeline (no GDAL on the laptop; 15 GB free).
- **Reader**: one function (`map-vehicles` successor) `GET areas?level&bbox&layer&source&make&from&to` → `{area_key,
  entities, value, avg}` + `as_of`; `GET points?bbox&layer` at point zoom; `GET area?key` → activity across layers.
- Target: pan/zoom shows cached geometry immediately, counts within ~300 ms, no spinner on boundaries.

## The web map (step 5)

MapLibre, modeled on iOS: zoom drives level; layer picker; filters (source, make, date window, event type); area
panel with each layer's activity; point panel for vehicle/org with source-listing link; URL state. Replaces `/map`,
`/atlas`, `PublicMap`, `NukeMap`, `CountyListingMap`, `ChoroplethMap`, `MarketGeographyMap`.

## iOS (step 6)

`CountyZIPDrill` reads the same reader and boundary tiles; the on-device fold and TIGERweb calls are removed.

## Delivery

Each step merges and is verified live before the next; the current `/map` stays until step 5 replaces it.
