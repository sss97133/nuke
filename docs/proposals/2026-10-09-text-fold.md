# Pre-mint memo: the text fold (2026-10-09)

**Status:** proposal, docs only. Nothing applied. Written by the unattended night run from read-only production reads
between 08:43Z and 08:50Z on 2026-10-09 (`scripts/data/q.sh`; samples use `TABLESAMPLE SYSTEM (1) REPEATABLE (20261009)`).
It follows the stance measurement in case ledger §13.5 and `docs/features/stance-fold/SPEC.md` and does not repeat them.

**Recommendation: do not mint a claims table, and do not declare the substrate yet.** The text fold already has two
homes and a writer. Field-shaped claims land in `field_evidence`, and claim atoms land in `vehicle_observations`
through `ingest-observation`. The writer is `batch-comment-discovery` with `claimLanding.ts`. The crowd side is nearly
empty: 198 comment claims in `field_evidence`, all written on one day in March, and no refinery atoms in a 1% sample of
the observation log. Declaring either table would flip five stacks on paper while no lot gains a crowd claim. The
repair is intake: a bounded, throttled run of the existing refinery with an assay, then a declaration once the crowd
side has a measured coverage.

**No gap that needs a mint.** The claim organ exists twice, and the grammar for claim atoms was settled on 2026-10-07
(#723: a claim is a comment atom in `vehicle_observations` with a `property_id`, guarded by the claim triggers; the
`ownership_relation` property is proposal `8a5f2264`, `add_property`, status **open** since 2026-10-07 01:33Z, so that

not a third.

### 2. Observations first?

Yes, and it already works that way. A claim read from a comment or description is testimony about testimony: the
`comment_refinery_atom` observation keys the source comment (`source_comment_id`), the property, the speaker
(`auction_comments.external_identity_id`, null on 0.16% of rows by pg_stats, 08:50Z) and the clocks. `field_evidence` is the per-field
consensus layer that a fold writes from those atoms, not a second place to land them.

### 3. DNA, trust vocabulary, CHECKed vocabularies

`vehicle_observations` has the full DNA set (listed above). `field_evidence` has `source_type` (72 distinct values, no
CHECK), `source_confidence` (0 to 100, CHECK), `status` (CHECK: pending, accepted, rejected, conflicted, superseded) and
`extracted_at` (equal to `created_at`), with no event clock of the claim and no source-atom key. Trust in the
SCHEMA_LAW T1/T2/T3 dialect: **Unknown** for both tables, not read tonight. The refinery's own vocabulary
(`statement_kind` assertion/question, `epistemic_status` asserted/uncertain/unknown/refused, categories A–E and Q in
`_shared/commentRefinery.ts`) lives in code, not in a CHECK.

### 4. Could a view do this? Corrections as supersession?

The S05 fold (per lot: what the crowd flagged that the seller did not state) is a read over two sides that already have
homes: description claims in `field_evidence` and comment atoms in `vehicle_observations`. It can be a view or a
bounded function keyed by lot and property, with no new table. Corrections supersede (`is_superseded`, `superseded_by`
on both tables).

### 5. Invariants as constraints, with attack tests

These already exist: the #723 validate and guard triggers on `vehicle_observations`, scoped to claim rows, and the unit
tests next to the writer (`batch-comment-discovery/claimLanding.test.ts`, `deriveComment.test.ts`). What's missing is a
measured precision floor per claim class before a reader uses the atoms. §13.5 measured 67–73% on two rule classes for
stance; claim classes A–E have no published precision.

### 6. Writers and registry

The writer is `batch-comment-discovery`: its `claimLanding.ts` (last changed 2026-10-02, 5e512be0f) lands atoms through
`ingest-observation` and marks `comment_claims_progress`; an older path in its `index.ts` writes `field_evidence`. No
pg_cron job calls it (`cron.job`, 08:48Z: the only matching jobs are `weekly-analyze-auction-comments`,
`discover-description-data` and `observation-discovery`, all inactive). Whether it is deployed now: **Unknown**; this run
does not probe the project. Registry: `vehicle_observations` is owned by `ingest-observation` (so atoms landed through it
are declared), and `field_evidence` is owned by `observationWriter`. The refinery calls a paid model
(`costCents` in its landing input), so a run is a spend decision.

### 7. Migration

None now. The order:
1. **Intake:** a bounded, throttled run of `batch-comment-discovery` on one stratified slice (for example the comments
   on lots that closed in one week). Its assay is atoms landed per comment read, with precision read on a sample per
   claim class.
2. **Fold:** the S05 reader as a view or bounded function over atoms and description claims, with a PG17 contract.
3. **Declare:** one `stack_substrates` row naming `vehicle_observations` (scoped by `extraction_method =
   'comment_refinery_atom'`) through the existing `schema_proposals` path with `evidence[]`, once step 1 has a measured
   coverage.
